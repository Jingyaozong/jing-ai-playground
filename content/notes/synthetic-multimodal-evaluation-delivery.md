> 虚构项目演练 · 编辑候选 · 待荆确认

本文完整虚构一个多模态评测委托，不是荆的真实项目，也不是脱敏复刻。这里没有视频、模型输出、评测分数或交付成果；所有项目名、需求和字段只为展示方法。页面写的是“准备怎样做”，不能被理解成“已经做完”。

虚构团队正在规划一款叫“片刻引擎”的短视频原型，希望生成六至十二秒的城市生活片段。产品方只说了一句：“新版本看起来更好了，帮我们系统评一下。”

评测工作的第一步，不是马上找人看视频，而是把“更好”变成一组可以观察、复核和决定下一步的问题。

## 一、先确认这次要做什么决定

这个虚构委托暂定回答：**候选版本是否具备进入下一轮内部试用的条件，以及下一轮数据应该优先补哪里。** 它不负责证明模型领先行业，也不直接作公开宣传结论。

需求确认单先写清以下边界：

| 项目项 | 本演练的约定 |
| --- | --- |
| 输入 | 文本 Prompt；部分任务可带虚构参考图或短对白 |
| 输出 | 计划生成六至十二秒 MP4；本页没有实际文件 |
| 任务场景 | 单人动作、多人关系、物体交互、环境运动、运镜与短对白 |
| 比较对象 | 基线版与候选版，用盲化代号显示；版本均为虚构 |
| 核心决定 | 是否进入下一轮内部试用；哪些问题必须先修 |
| 交付物 | 评测说明、样本清单、逐项记录、问题台账、复验单与报告模板 |
| 明确不做 | 行业排名、法律意见、营销背书和未经核对的能力结论 |

如果产品方关心的是广告成片，和只想验证动作连续性，样本与权重会完全不同。先写决策问题，才能避免最后交出一份“有很多分数，却不能支持任何决定”的报告。

## 二、把模糊要求改成可观察行为

“自然”“稳定”“像真的”都不能直接成为验收规则。它们需要被拆成观看位置、证据形式和不确定时的处理方式。

| 模糊说法 | 改写成什么检查 | 证据怎样留 | 无法判断怎么办 |
| --- | --- | --- | --- |
| 人物稳定 | 人脸、发型、服装与身份是否在镜头内持续一致 | 时间点、帧段与变化描述 | 标记待确认，不补猜身份 |
| 动作自然 | 轨迹、接触、受力与前后状态是否连续 | 起止时间、关键帧与播放记录 | 区分播放器卡顿与文件异常 |
| 镜头舒服 | 景别、机位、运镜是否服务指定信息与节奏 | 对照 Prompt 中的镜头要求 | 没有镜头要求时不擅自扣分 |
| 声音对得上 | 嘴型、动作、对白、音效和环境音是否同步 | 音画时间段与偏移现象 | 无音轨时记不适用 |

每条要求还要约定严重度。演练采用“阻断、重要、轻微”三个等级，但不预设真实阈值：阻断项是否一票否决、重要问题允许多少、轻微问题怎样汇总，都要在试评后由项目双方确认。

## 三、评测集不是一份随机清单

计划中的评测集分成三套，各自回答不同问题。

### 标准测试集

覆盖主要业务场景，保留一部分固定锚点，用于后续版本纵向对照。锚点不能因为某次表现不好就悄悄替换；变更时要保留原因与版本。

### Bad Case 专项集

把历史上已经定义清楚的高频问题改写成专项任务，例如多人关系、手与物体接触、文字生成、人物跨镜一致性。这里的“历史问题”只是一种建集方法；本虚构案例没有导入任何真实历史样本。

### 压力测试集

覆盖遮挡、快速运动、复杂反射、烟水布料、多主体交互、长指令、多镜头与音画同步等边界。它用于暴露能力边界，不能与普通分布混在一起计算一个看似总体的通过率。

正式抽样前还要做四件事：

- 按任务类型、主体数量、镜头方式和风险标签分层，避免清单被简单场景占满。
- 与可获得的训练或历史集合做去重；无法确认时明确记录未知范围。
- 为开放答案建立同义归一规则，为不可回答或证据不足的情况保留合法状态。
- 冻结本轮样本清单与规则版本；临时新增问题单独进入补充批次。

本演练没有给出样本数量。数量应在真实任务中依据场景覆盖、预算、置信要求和试评产能共同决定，不能把一个漂亮的整数包装成通用答案。

## 四、用八维记录，不急着压成一个总分

每条输出沿用 [视频评测固定八维框架](/notes/video-evaluation-eight-dimensions/)：语义遵循、基础画质、美学表现、主体与场景一致性、时序与动作连续性、结构与物理合理性、镜头语言与叙事、音画与安全。

八维是固定观察位置，不代表每条样本八项都适用。没有声音的视频，音画同步应记“不适用”，不能写成通过；没有人物的场景，也不应该硬评人脸一致性。

单条记录建议至少保留：

需要开始填写时，可打开本站的 [多模态评测记录台](/tools/multimodal-evaluation/)。它只在浏览器当前页面处理文字记录，不上传视频或 CSV，也不会自动生成评测结论。

| 字段 | 记录目的 |
| --- | --- |
| 样本与输出 ID | 找回原始任务与文件 |
| Prompt 与素材版本 | 知道评的是哪一版输入 |
| 模型盲化代号 | 减少版本印象影响判断 |
| 维度与子标签 | 定位问题落在哪个观察位置 |
| 状态 | 满足、不满足、无法判断或不适用 |
| 严重度 | 区分阻断、重要与轻微影响 |
| 时间段与证据 | 让另一位评测者能复现观看位置 |
| 规则版本 | 解释当时依据哪套口径 |
| 复核状态 | 区分初评、争议、已裁决与待复验 |

总分如果确实服务业务决定，可以在口径稳定后再设计。但阻断项、美学偏好和不适用项不能简单平均；一个数字也不能替代问题分布和证据。

### 一张填好的演练记录，应该长什么样

以下是**完全虚构的纸面记录**。任务、时间码和“观察”都是为演示填写方式编写的剧本，不对应任何视频文件、模型运行或真实评测结果，不能导入工具后当作已评样本。只有拿到实际输出并逐帧复看，才可以把演练状态改成真实判定。

任务卡 `DEMO-CUP-01`：设想一段八秒单镜城市咖啡店片段。画面中只有一位店员和一位顾客；店员用右手把一只白纸杯递给顾客，顾客接稳后店员才松手。固定中景，不切镜，不出现第二只杯子；无声输出。输出文件 ID：**不存在**。规则版本：演示草案 `R0`，待荆确认。

1. **语义遵循。** 假设 02.4 秒出现第二只纸杯，可记“不满足”、重要；限制条件被违反。证据栏应记录秒数和杯子位置，并回看 Prompt 是否真的写了“只有一只”。
2. **基础画质。** 纸面情境没有清晰度证据，只能记“无法判断”。要等实际文件和原始分辨率，不能从一张截图推断整段质量。
3. **美学表现。** 即使设想中的构图平衡，也先记“待记录”，因为偏好标准尚未校准。先补焦点和构图参考，再让两位评测者独立观看。
4. **主体与场景一致性。** 假设服装和柜台在 00—08 秒没有变化，才可暂记“满足”；实测至少保留首、中、尾对照，不能凭单帧断言。
5. **时序与动作连续性。** 假设顾客尚未接稳，店员已经松手，可记“不满足”、重要。证据位置是 04.1—04.6 秒；还要排除播放器丢帧。
6. **结构与物理合理性。** 假设同一交接中杯底穿过掌心，可另记“不满足”、重要。标记 04.3 秒接触点，与时序异常交叉引用，避免把一个样本重复计数。
7. **镜头语言与叙事。** 若全片固定中景、交接动作可辨认，可记“满足”；仍需核实有无隐藏切镜。本任务不要求完整故事。
8. **音画与安全。** 任务明确无声，嘴型和音效同步记“不适用”；安全与授权仍是“待核查”。无声不等于安全通过，主体、品牌和素材许可须另查。

这张演练表故意把“想象中的现象”和“真实证据”隔开。若它是一条真记录，工具里的时间段必须指向实际可回放的输出；没有文件时，八维状态仍应保持待记录，而不是把上表的假设填成通过率。

下一步的归因卡也只写假设：先核对输入是否含单杯与接稳后松手的约束，再检查文件与 Prompt 是否配对、播放是否丢帧、规则是否区分“交接”与“释放”，最后才提出模型能力问题。假如未来真有同类异常并完成复核，才把“手物交接顺序”收进专项集，固定输入条件复验。没有实测文件，本案例的复验状态始终是**待执行**。

## 五、先试评，再决定能否放量

正式执行前，从三套集合中各取少量代表任务组成模拟试评包。两位评测者独立观看，再对照差异，不先互相讨论答案。

试评要发现四类问题：

1. Prompt 本身是否有歧义，导致无法形成唯一判断。
2. 维度与子标签是否重叠，同一现象被不同人放到不同位置。
3. 严重度边界是否清楚，是否出现“看着不舒服就判阻断”。
4. 工具能否保存时间段、证据、版本和复核状态，导出后是否仍能对账。

只有争议规则获得裁决、人员理解通过复标、导入导出校验正常，才进入下一批。真实项目还应预先确认一致率或准确率门槛；本页没有执行试评，因此没有门槛结果、人员表现或放量结论。

## 六、生产记录怎样避免丢证据

计划中的观看顺序是：先按正常速度完整看一遍，理解任务和叙事；再定位疑点，按需慢放或逐帧检查；最后回到正常速度确认问题是否真的影响整体观看。

评测界面不只放“通过 / 不通过”两个按钮。它要同时显示 Prompt、素材版本、适用维度、证据时间段、严重度、问题标签、规则入口与复核状态。保存失败、文件打不开或音轨缺失进入流程问题，不应该被写成模型失败。

批次监控分别看已评数量、待复核、争议积压、无效文件和规则变更影响范围。不同难度与风险层的数据分开呈现，不能用未经校正的错误数量给人员排能力名次。

## 七、Bad Case 先列假设，再找原因

下面三行只是虚构推演，没有对应视频，也不是模型已出现的问题：

| 假设现象 | 可能涉及的层 | 下一步证据 | 可能的数据动作 |
| --- | --- | --- | --- |
| 手接住纸杯后杯子短暂穿过手掌 | 输入、规则、评测流程或模型能力待排查 | 核对原 Prompt、文件配对、接触规则与异常帧段 | 若可复现，再纳入手物接触专项集 |
| 转场后人物外套颜色改变 | 剧情要求、主体一致性规则或模型能力待排查 | 确认是否要求换装，复核跨镜身份与服装条件 | 补充跨镜属性保持或明确换装样本 |
| 雨声持续但画面已进入室内 | 音轨关联、剪辑流程或音画生成能力待排查 | 检查音轨文件、时间线和场景切换位置 | 构建环境音随场景切换的边界任务 |

归因按数据、规则、执行理解、工具流程和模型能力五层逐项排查。证据不足时保留“待确认”；只有排除错配、规则歧义与流程异常后，才能把可复现问题送给算法侧验证。

高频且已确认的问题可以形成专项集，但新集合要登记来源、适用版本和退出条件。否则专项集只会越积越多，却没人知道问题是否已经关闭。

## 八、优化建议必须能回到证据

评测报告中的建议不写“多加一些高质量数据”。它应对应能力维度、问题证据和预期验证方式。

例如，如果多主体位置关系反复失败，建议可以拆成：检查现有关系描述是否一致；补充左右、前后、遮挡与交换位置的对照样本；保持主体数量和场景相近，只改变关系；再用固定专项集复验。

如果美学分歧大，先检查偏好标准和参考案例，而不是直接把少数评测者的口味写成模型缺陷。自动指标可以辅助清晰度、OCR 或一致性检查，但美学、自然度与叙事仍应保留人工判断和分歧记录。

## 九、交付的不是一张排行榜

这个虚构项目计划交付七部分：

1. 评测说明：决策问题、范围、版本、样本分层和适用规则。
2. 样本清单：输入、标签、集合归属、去重状态与文件映射。
3. 逐项记录：八维状态、严重度、证据和复核轨迹。
4. 问题台账：分类、批次、来源、原因假设与负责人角色。
5. 复验记录：修改内容、受影响范围、复验集合和关闭依据。
6. 评测报告：优势、限制、主要问题分布、风险与下一步建议。
7. 交付清单：文件校验、规则版本、已知限制和未关闭事项。

报告首页先回答“能不能进入下一轮、为什么、还有什么风险”，再展示各维度与场景。没有证据的判断不写成结论；压力集表现不外推到普通分布；候选版局部更好也不等于整体升级。

一段可复用的报告骨架可以这样写：

> 本轮评测面向【待填写决策】，覆盖【待填写范围】。在【规则版本】下，候选版的可确认优势是【待证据】，主要限制是【待证据】。尚未解决的阻断项为【待填写】。建议下一步【修订规则 / 补充数据 / 修复流程 / 复验模型】；在复验完成前，不作【待填写外推结论】。

这只是空模板，不是本案例的评测结论。

## 十、最后通过四道交付关

交付前沿用 [数据交付四道关](/notes/dataset-release-gates/)：格式能否按约定读取；无效、损坏、重复和待复核数据是否隔离；抽检与复验是否闭环；版本、批次、返修和未解决问题是否可追溯。

最终包中的原始输入、生成文件、评测记录和报告要能通过 ID 相互找到。任何删除、合并或替换都保留映射；规则更新后说明影响哪些旧记录，不能只覆盖文件名。

## 这份演练展示了什么

从一句“帮我系统评一下”，到一份能支持决策的报告，中间需要需求边界、分层评测集、八维记录、校准试评、证据留存、五层归因、数据建议、复验和交付门禁。

这套路径展示的是荆提供的方法如何连接起来，不是虚构一段项目履历。页面仍是编辑候选，待荆确认表达；无需、也不应该补入任何真实客户资料。
