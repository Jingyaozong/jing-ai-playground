办公 Agent 评估最容易漏掉的，是“看起来做完了”的任务。它可能生成了一个能打开的文件，也可能最后回复“已经完成”，但统计口径、保存位置或关键字段仍然不符合要求。

一份有用的复核记录，需要把**任务要求、可观察的执行过程、最终产物**接在一起。读完之后，下一位同事应当知道在哪里重现问题、先查什么、怎样判断修改有效。

## 先把“完成”写清楚

拿到一句“帮我整理销售表”，先补齐验收条件。否则一个人按毛销售额算，另一个人按净收入算，双方都可能觉得自己的结果正确。

| 要确认的事 | 可执行的写法 |
| --- | --- |
| 输入范围 | 指定文件、工作表、日期区间和时区；明确是否包含隐藏行 |
| 计算口径 | 退款、取消、空值、币种、重复订单分别怎样处理 |
| 交付要求 | 文件名、目录、格式、必需字段、公式与可编辑性 |
| 使用边界 | 哪些文件可读写，哪些动作需要人工确认，原始文件是否必须保留 |
| 判定依据 | 核对单元格、重算结果、产物截图或校验脚本，以及规则版本 |

“文件存在”“文件可打开”“内容正确”是三个检查项。生成 PPT、HTML 或 PDF 时，还要另外检查阅读顺序、字体、遮挡、分页和导出后的实际显示。视觉质量可以单独评估，不宜用一个漂亮总分抵消事实错误。

## 结果与过程，分别复核

**结果层**看交付物是否满足约定：内容、数值、结构、位置和可用性。最终回复只是 Agent 的完成声明，需要与产物证据核对。

**过程层**看可观察的动作：选了什么工具、传入哪些参数、工具返回什么、后续动作怎样使用返回、出错后是否恢复。这里的轨迹指动作日志与可见中间结果，不需要取得或推测模型内部思维链。

Workflow 通常更依赖预先安排的步骤；Agent 可以根据当前信息选择后续动作。实际系统常混合两者，复核时应以真实工具边界与可观察行为为准，不必先给系统贴一个绝对标签。

## 找到首个偏离点

下面用一个极小的虚构任务演练：三个订单分别为已支付 120 元、已退款 80 元、已取消 40 元。要求排除退款与取消，生成合计为 120 元的可编辑销售表。

| 步骤 | 可观察记录 | 复核关注点 |
| --- | --- | --- |
| S1 读取 | 三条订单均被读取 | 输入是否完整，状态字段是否可用 |
| S2 汇总 | 参数只排除已取消，返回 200 | 工具成功执行了错误口径；这里已经偏离要求 |
| S3 保存 | 返回“文件占用”错误 | 显式执行报错，但不是最早的任务偏离 |
| S4 重试 | 保存成功，仍写入 200 | 重试解决了保存问题，没有修复计算口径 |
| S5 回复 | 声称任务已完成 | 声明与验收要求不一致，仍需打开产物复核 |

这个例子有两条不同的线索：首个显式报错在 S3，首个可观察的任务偏离在 S2。直接拿第一条 error 当根因，会让修正停留在文件重试上。

可把复核顺序固定下来：

1. 先找到最终不符合哪条验收条件。
2. 逆向追踪这个结果来自哪个返回、参数或输入。
3. 找到当前证据支持的最早偏离点，并检查更早步骤是否已经埋下问题。
4. 标出受影响的后续步骤；区分原始问题、传播结果与独立故障。
5. 日志有缺失时写“目前可见的最早偏离”，保留未确认范围。

可以在 [轨迹复核台](/tools/agent-trace-review/) 载入这份虚构日志。工具会标出日志中的 error；偏离点和原因仍由复核者填写。

## 把现象和原因分开

先使用稳定的现象分类，再写可能原因。同一个“结果错误”，背后可能是任务规则含糊，也可能是参数、状态或结果整合出了问题。

| 分类入口 | 可复核的问题 |
| --- | --- |
| 任务与规则 | 用户要求、标准答案或评分规则是否互相冲突 |
| 规划与拆解 | 是否遗漏必要步骤、依赖顺序或验收动作 |
| 工具选择 | 当前工具是否具备任务需要的能力 |
| 参数与口径 | 文件、工作表、筛选条件、单位和路径是否正确 |
| 执行与环境 | 权限、依赖、文件占用、接口返回是否阻断执行 |
| 状态与上下文 | 是否使用旧文件、丢掉约束、重复写入或覆盖中间结果 |
| 结果整合 | 是否误读返回、遗漏限制，或在未验证时声称完成 |

以 S2 为例，事实是“排除参数缺少 refunded，返回 200”；“没有保留用户口径”是原因假设。还需要检查输入是否清晰、接口说明是否易误解、相同版本能否复现，才能把问题进一步归到某个能力环节。

报告可以写成：

```text
现象：输出合计 200，与验收要求 120 不符。
位置：S2 aggregate_orders；S1 返回中包含 refunded 状态。
依据：S2 排除列表只有 cancelled，漏掉了任务要求的 refunded。
影响：S4 继续写入错误合计；保存重试不修复数据口径。
假设：任务约束没有完整映射到参数，尚未验证根因。
下一步：固定输入和环境，仅修正排除参数后重跑并重开产物核对；
        再用同类不同状态组合的样本检查是否复现。
```

这是一份虚构记录的写法示范。重跑结果尚不存在，不能写成“已修复”或“准确率提升”。

## 评估集怎样拉开差异

从办公任务拆能力，而不是先堆题量。文件任务可以覆盖路径选择、读写、保留原件；数据任务覆盖筛选、计算、单位与缺失值；文档任务覆盖结构、引用、编辑和导出。

准备三类互补的样本：固定基准集用于版本比较，高频问题集用于回归，压力集覆盖长文件、多轮约束、工具失败和复杂依赖。要保留“做对了”和“能够恢复”的样本，不能只看失败日志。

每个 Case 至少包含：任务、输入版本、预期产物、可执行验收项、能力标签、难度、允许工具、运行条件和裁决记录。主观项给正反例；规则不确定的样本先讨论，不强塞进确定对错的统计。

为避免难度变化制造“提升”，新旧版本应在同一组冻结样本、相同工具权限和资源限制下比较。训练数据去重、参考答案复核、时间敏感数据版本也要在样本清单里记录。

## 成功率要有分母

建议分别报告任务完成、文件可用、内容正确、错误恢复与成本。多次运行时按运行记录统计，并同时保留 Case 数和每个 Case 的重复次数。

例如“任务完成率”可定义为：满足全部必需验收项的运行数 ÷ 纳入评估的运行数。尚未验收的运行单列；环境故障是否排除，要在运行前约定并同时披露排除数。不能在看见结果后临时换分母。

工具调用 error 的占比使用调用次数作分母；任务成功率使用运行数作分母。两者不能直接相减。总延迟也不能简单把嵌套或并行调用耗时相加。

竞品比较还应记录产品或模型版本、日期、工具、账号权限、输入、时间与调用预算、失败重试规则。公开 Benchmark 可以帮助发现能力缺口，但不能直接代替特定办公业务的验收。

## 让结论能被接走

供应商结果二次复核时，保留原判定、复核判定、分歧原因和最终裁决。争议样本不要悄悄覆盖；规则更新以后标出受影响批次，重新抽查。

交付一个问题时，把 Case ID、规则与输入版本、原始轨迹、关键步骤、产物证据、现象标签、原因假设、下一步验证和未解决项放在一起。对于高频错误，按任务、版本、规则批次和触发条件下钻，再决定是否补专项评估集。

工具能节省的是整理、定位和重复书写的时间。是否完成任务、问题是否具有代表性、修正是否有效，仍需要对应证据。

下一步可以先做一条完整记录：打开 [轨迹复核台](/tools/agent-trace-review/)，从虚构演练理解结构，再用获准公开或独立合成的日志实践。批量问题闭环可接着读 [问题复盘：从现象到复验](/notes/bad-case-review-loop/)。
