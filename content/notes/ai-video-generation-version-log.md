AI 视频生成最容易丢失的，往往不是文件，而是**这个文件为什么出现、与上一版差在哪里、为什么没有被采用**。

硬盘里可能同时存在 `video_12.mp4`、`video_12_final.mp4`、`video_12_final2.mp4` 和 `真的最终版.mp4`。生成平台里还有几十条相似记录。等镜头需要返工时，已经没人能回答：当时用了哪张参考图？改了哪一句 Prompt？哪一版动作最好但人物变脸？剪辑里采用的是整段，还是第 1.8 到 4.6 秒？

留档不是为了保存一切，而是为了让一次选择**可以解释、可以回找、可以继续迭代**。

> [!KEY POINT]
> 最小留档单位不是一个 MP4，而是一条决策链：它属于哪个镜头、来自哪个生成批次、用了什么输入与设置、结果哪里可用、为什么入选或淘汰、最终怎样进入剪辑。

## 先分清三件事：镜头、批次、候选版本

这三层如果混在一起，文件名很快就会失效。

| 层级 | 它回答的问题 | 建议编号 |
| --- | --- | --- |
| 镜头 Shot | 故事里要完成什么任务？ | `S06` |
| 批次 Batch | 这一次保持了哪些输入和设置？ | `B03` |
| 候选 Take | 同一批次返回的第几个结果？ | `T02` |

完整候选 ID 可以写成：

```text
S06-B03-T02
```

它表示镜头 06 的第三次生成批次中的第二个候选。模型、日期、状态和评价不要全塞进文件名；它们更适合进入记录表。文件名只承担一个任务：**稳定指向同一条记录。**

[Runway 的 Sessions 官方说明](https://help.runwayml.com/hc/en-us/articles/33545310653203-Generating-with-Sessions)把 Session 描述为一组相关生成的组织结构，尤其适合围绕同一风格、场景或镜头比较与迭代；Projects 则能进一步组织 Assets、Sessions 和 Workflows。这个层级关系很适合作为提醒：平台里的会话可以帮助找回生成，但项目仍然需要自己的镜头编号和决策记录。

## 第一层：镜头卡记录“什么叫完成”

同一个镜头可能换模型、改参考图、生成十几个版本，但它的叙事职责不应该跟着每次 Prompt 漂移。

一张镜头卡至少记录：

- 镜号与场次；
- 这一镜要让观众看见或理解什么；
- 计划景别、机位和时长；
- 入镜人物、场景和关键道具；
- 必须锁定的连续性事实；
- 与上一镜、下一镜的接口；
- 最低可用标准。

例如：

```text
镜号：S06
职责：人物第一次意识到门外有人。
最低可用：人物先停住写信，再抬头看向画面右侧房门；信封保持拆开；镜头至少有 2 秒可用于接反打。
必须锁定：人物服装、东墙房门、右手信纸、北窗冷光。
```

“最低可用”比“电影感、震撼、高质量”更重要。它决定候选版本是否真正能剪进故事，而不是能否成为一张好看的封面。

## 第二层：批次卡记录真正改变了什么

一次批次是一个可比较的小实验。批次内尽量保持输入和设置相同，只让系统返回多个候选；准备测试新 Prompt、参考图或模型时，再建立新批次。

批次卡建议保留以下字段：

| 字段 | 记录内容 |
| --- | --- |
| 生成时间 | 日期、时间和必要的时区 |
| 平台与模型 | 平台、模型名称或 ID、可见版本 |
| 生成方式 | 文生视频、图生视频、首尾帧、延长或参考图 |
| Prompt | 完整原文，不只保存修改后的最新版 |
| 输入资产 | 首帧、尾帧、角色参考、场景参考及其文件 ID |
| 参数 | 时长、比例、分辨率、Seed、负面提示等实际可见设置 |
| 本批变量 | 相比上一个批次只改变了什么 |
| 平台记录 | Session、Asset 或任务链接；必要时保存截图 |

[Runway 的资产分享说明](https://help.runwayml.com/hc/en-us/articles/25562277393427-How-to-share-an-asset)指出，Runway 生成资产的分享页面可以包含文本、图片或视频输入、Seed 等生成详情；[资产管理说明](https://help.runwayml.com/hc/en-us/articles/23998498329107-How-to-organize-assets)则说明生成结果会进入 All Generations，也可进一步放入文件夹。平台记录值得保留，但不要把它当作唯一档案：链接权限、产品界面、账号和平台保存策略都可能变化，本地项目还应保存必要输入、输出与文字记录。

### Seed 要记录，但不要神化

[Google Cloud 的 Veo 首尾帧生成文档](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/video/generate-videos-from-first-and-last-frames)列出了 Prompt、首帧、尾帧、模型 ID、画幅、时长、结果数量、分辨率、负面提示和 Seed 等请求要素，并说明在其他参数不变时，指定 Seed 会引导模型生成相同视频。

这条说明只适用于文档所描述的具体模型与接口条件。生产记录里仍应同时保存模型 ID、输入资产和完整参数，不能把 Seed 当成跨模型、跨版本、跨平台的通用复现钥匙。平台更新、模型版本和未公开的服务变化都可能影响结果。

## 第三层：候选卡记录“结果发生了什么”

同一批次的候选共享输入，但结果并不共享质量。每个 Take 不需要写长评，只需要回答四件事：

1. 哪一段可用；
2. 最明显的优点；
3. 最先导致淘汰的问题；
4. 当前状态。

建议使用有限状态，而不是无限增加“也许能用”“有点喜欢”“以后再看”：

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| NEW | 尚未完整检查 | 至少原速看一遍，再放进相邻镜头环境 |
| SHORTLIST | 有明确可用区间 | 与同镜候选并排比较 |
| SELECT | 当前剪辑采用 | 记录时间码与后期处理 |
| HOLD | 有价值但不适合当前剪辑 | 写清保留原因，避免变成隐藏废片 |
| REJECT | 有明确致命问题 | 记录第一个淘汰原因即可 |

`SELECT` 不是“永远最佳”，只是当前剪辑版本的采用状态。换了前后镜头、对白长度或音乐节奏，它仍可能被另一个候选替代。

## 淘汰原因要具体到“下一次能改变什么”

只写“不好”“不够电影感”“AI 味重”，下一次仍然不知道该改哪里。建议让每个淘汰版本只选一个**首要原因**，再补充一句可观察事实。

| 代码 | 淘汰类别 | 可观察的写法 |
| --- | --- | --- |
| NAR | 叙事没有完成 | 人物没有看向房门，镜头没有兑现“听见声音”的任务 |
| ID | 人物或主体漂移 | 抬头后五官、发型或服装结构发生变化 |
| SCN | 场景或道具漂移 | 东墙房门消失，手里的信纸重新变成封闭信封 |
| MOT | 动作与物理错误 | 手臂穿过桌面，起身动作没有可用的中间阶段 |
| CAM | 机位或构图错误 | 摄影机无因绕到轴线另一侧，人物视线方向反转 |
| TMP | 时间连续性错误 | 雨量、灯光或人物状态在镜头内部突然重置 |
| SND | 声音不可用 | 台词被截断，环境声与相邻镜头无法衔接 |
| TEC | 技术规格错误 | 比例、分辨率、时长或文件损坏不符合交付要求 |
| CUT | 单镜可看但无法组接 | 没有需要的入点或出点，与前后镜动作方向冲突 |

例如：

```text
S06-B03-T02 / REJECT / SCN
00:03.4 起，右手信纸变回封闭信封；破坏上一镜已经拆信的状态。
```

这条记录下一次可以直接转化为锁定项。相比“画面不稳定”，它明确指出了对象、时间和错误类型。

## 比较候选时，先同批，再跨批

同批比较回答“相同条件下哪个结果更可用”；跨批比较回答“这次修改有没有解决目标问题”。两种比较不要混在一起。

[Frame.io V4 的 Comparison Viewer](https://help.frame.io/en/articles/9952618-comparison-viewer)支持把两个资产并排比较，并提供联动播放、缩放和评论；静态资产还可以使用叠加与像素差异视图。[Frame.io 的版本堆叠说明](https://support.frame.io/en/articles/4431-version-stacking-and-comparison-mode-legacy)也展示了把修订版本组织在同一个版本栈中的思路。

即使不用 Frame.io，也可以保留同样的比较纪律：

1. 先把同一镜头的候选放到同一个 Bin、文件夹或时间线轨道；
2. 统一入点，从关键动作前一小段开始播放；
3. 第一轮只淘汰致命错误，不比较细微审美；
4. 第二轮把短名单放进前后镜头之间；
5. 最后才比较色彩、纹理和微小表演差异。

单独循环播放时最吸引人的版本，不一定是剪辑里最有用的版本。真正的比较环境应包含相邻镜头、声音和计划时长。

## 选中以后，还要记录“采用了哪一段”

生成结果被选中不等于整段都被使用。采用记录至少包括：

```text
采用候选：S06-B04-T01
源文件：S06-B04-T01.mp4
采用区间：源文件 00:01.18–00:04.62
剪辑位置：时间线 01:02:14:08–01:02:17:22
速度处理：96%
画面处理：裁切右侧 4%；轻微稳定；匹配上一镜冷蓝窗光
声音处理：弃用生成音频；沿用场景雨声底；门外敲击声后加
替换原因：B03-T04 的抬头表演更自然，但信纸状态错误
```

[Adobe Premiere 的 Metadata 面板说明](https://helpx.adobe.com/premiere/desktop/organize-media/edit-metadata/view-clip-data-in-the-metadata-panel.html)列出 Clip Name、Log Note、Timecode 等项目级镜头信息；[Premiere 的元数据说明](https://helpx.adobe.com/uk/premiere/desktop/organize-media/edit-metadata/metadata-in-premiere.html)区分文件元数据和只存在于项目文件中的 Clip Metadata。也就是说，同一个源文件可以在不同剪辑实例里拥有不同说明。重要决策仍建议同步到项目外部的简单记录表，避免只存在于某个剪辑工程中。

## 一套够用的文件夹和命名法

不要为了“专业”建立十几层空目录。单人项目先保证一眼能找到输入、候选、采用版和记录表：

```text
PROJECT/
├─ 01_REFERENCES/
│  ├─ CHARACTER/
│  └─ SCENE/
├─ 02_GENERATIONS/
│  ├─ S05/
│  ├─ S06/
│  │  ├─ B01/
│  │  ├─ B02/
│  │  └─ B03/
│  └─ S07/
├─ 03_SELECTS/
├─ 04_EDIT/
└─ shot-version-log.csv
```

生成文件使用稳定 ID：

```text
S06-B03-T01.mp4
S06-B03-T02.mp4
S06-B03-T03.mp4
```

导出的剪辑版本才使用日期和版本号：

```text
film-cut_2026-08-28_v07.mp4
```

不要覆盖旧文件，也不要把 `final` 当成状态系统。版本号表达顺序，记录表表达采用关系，二者分工更清楚。

## 每轮生成后的五分钟收口

一次生成结束后，先完成这组动作，再开下一轮：

- 把结果归入正确的镜号与批次；
- 保存完整 Prompt、参考资产和可见参数；
- 为每个候选标记状态；
- 淘汰版本只写一个首要原因；
- 短名单记录可用时间段；
- 当前采用版记录剪辑区间和处理；
- 下一批只声明一个主要改动目标。

> [!TIP]
> 如果一轮生成结束后无法说清“下一批只改什么”，先不要继续生成。回看淘汰原因：如果问题分散在人物、场景、动作和机位四层，应该拆镜或重做输入；如果问题集中在同一个对象，才适合针对它继续迭代。

## 最小版本记录模板

```text
候选 ID：
镜头职责：
平台 / 模型：
生成方式：
Prompt：
输入资产：
时长 / 比例 / 分辨率 / Seed：
相比上一批只改变：

状态：NEW / SHORTLIST / SELECT / HOLD / REJECT
可用区间：
首要优点：
首要淘汰原因：NAR / ID / SCN / MOT / CAM / TMP / SND / TEC / CUT
观察事实：
平台记录链接：
剪辑采用区间与处理：
```

## 留档的终点不是整齐，而是少走一次回头路

好的版本记录不会让生成结果自动变好，也不会替你判断哪一镜最动人。它做的是更朴素的事：当人物又变脸、房间又换方向、动作又断掉时，你能找到问题从哪一批开始；当某一镜需要返工时，你能复用有效输入；当剪辑节奏改变时，你能重新找到被保留的另一段动作。

最终应该留下的，不是一座没人敢整理的素材坟场，而是一条可追踪的选择路径：**我们要完成什么，试过什么，看见了什么，为什么这样选，下一次只改什么。**
