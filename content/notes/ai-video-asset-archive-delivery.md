AI 视频项目最容易在“看起来快做完”的时候失控。

生成文件散在下载目录里，文件名叫 `video_7.mp4`；同一镜头有十几个候选，却不知道哪个 Prompt 生成了哪个结果；剪辑工程引用着桌面上的临时文件；交付以后才发现字幕、字体、音乐授权或无字母版没有一起留下。此时继续生成并不能解决问题，因为问题已经从“画面好不好”变成了“素材能不能被识别、追踪和恢复”。

归档不是把文件拖进一个大文件夹。它至少要回答五个问题：

1. 这是什么项目、哪一场、哪一镜？
2. 它从哪个版本发展而来？
3. 为什么采用或淘汰？
4. 工程在另一台电脑上能否重新打开？
5. 接收方拿到的是否就是双方约定的交付物？

> [!KEY POINT]
> 一个可靠的项目，不是“我记得文件在哪里”，而是离开当前电脑和当前记忆以后，仍能通过稳定编号、目录、清单和验证重新找到关系。

## 先分清：整理、备份、归档和交付不是一件事

这四个动作经常被混在一起，但它们解决的问题不同。

| 动作 | 主要问题 | 典型结果 |
| --- | --- | --- |
| 整理 | 当前制作时怎样快速找到素材 | 稳定目录、镜头编号、版本记录 |
| 备份 | 工作盘损坏或误删后怎样恢复 | 独立副本、异地副本、恢复测试 |
| 归档 | 项目结束后怎样长期保留 | 收集后的工程、必要源文件、说明与校验信息 |
| 交付 | 接收方需要拿到什么 | 约定格式、母版、字幕、音频、清单与授权说明 |

同步盘也不自动等于备份。文件被误删、覆盖或同步错误时，变化可能同时传播到其他设备；有没有足够的版本历史、离线副本和恢复能力，要看具体服务与配置。

## 一个文件必须先有稳定身份

不要从 `final.mp4` 开始命名。先给每个镜头一个不会随内容变化的身份，例如：

```text
SC03_SH014
```

- `SC03`：第三场
- `SH014`：第十四镜

镜头从远景改成近景、从模型 A 换到模型 B、从五秒延长到八秒，这个身份仍然不变。版本变化放在其他字段里，不要重新发明镜头编号。

一个实用但非强制的文件名可以是：

```text
MYS_SC03_SH014_turn-door_g24_v003_20260829.mp4
```

| 字段 | 作用 | 建议 |
| --- | --- | --- |
| `MYS` | 项目短码 | 2–6 个大写字母或数字 |
| `SC03_SH014` | 场与镜头身份 | 固定宽度，便于排序 |
| `turn-door` | 一眼可读的内容提示 | 简短、不要写整句 Prompt |
| `g24` | 生成批次 | 同批候选共享编号 |
| `v003` | 人工确认的版本链 | 只递增，不覆盖旧版 |
| `20260829` | 生成或导出日期 | 使用固定 `YYYYMMDD` |

版本号和生成批次不要混用。`g24` 表示第二十四批机器输出，可能包含四个候选；`v003` 表示其中一个候选进入人工版本链后的第三次修改。这样才能同时看见“生成了多少”和“真正迭代了几版”。

> [!BAD CASE]
> `final.mp4`、`final2.mp4`、`final_真的.mp4` 只记录了当时的情绪，没有记录素材身份、父版本、审核状态或交付用途。

## 文件名不是数据库，另外保留一张版本账

文件名适合快速辨认，不适合承载全部信息。模型版本、参考图、Prompt、随机种子、分辨率、授权状态、采用区间和淘汰原因应该放进版本记录或素材清单。

[Adobe 的 Premiere 元数据说明](https://helpx.adobe.com/premiere/desktop/organize-media/edit-metadata/metadata-in-premiere.html)区分文件元数据和工程内的 Clip 元数据：前者描述源文件并可随素材流转，后者只存在于特定工程中。官方文档还说明，Dynamic Media 字段可以记录场次、拍摄地点等视频制作信息。它提醒我们：文件名只是入口，跨工具流转的信息还需要元数据或外部清单。

最小版本账可以使用 CSV、表格或 Markdown，至少包含：

| 字段 | 记录内容 |
| --- | --- |
| asset_id | 稳定镜头或素材编号 |
| file_name | 当前实际文件名 |
| parent_version | 从哪个版本继续生成或修改 |
| created_at | 生成、导出或接收时间 |
| tool_model | 工具与模型版本；未知就明确写未知 |
| input_refs | 参考图、首尾帧、音频或控制素材 |
| prompt_snapshot | 当次实际使用的 Prompt 快照 |
| output_spec | 时长、比例、分辨率、帧率、编码 |
| decision | 候选、采用、淘汰、待复核或已交付 |
| reason | 为什么采用或淘汰 |
| rights_note | 来源、授权、限制或待确认项 |

[Frame.io 的版本堆叠说明](https://support.frame.io/en/articles/4431-version-stacking-and-comparison-mode-legacy)把同一资产的修订放进一个 version stack，并保留旧版本供比较。是否使用 Frame.io 并不重要，重要的是数据关系：新版应该指向同一资产，旧版仍可回看，而不是用同名文件覆盖。

## 目录按生产阶段分，不按软件分

只按软件建立 `Runway`、`Premiere`、`Photoshop` 文件夹，换工具以后会立刻混乱。更稳定的主结构是按素材在生产中的职责来分：

```text
MYS_project/
├─ 00_ADMIN/          # brief、计划、授权、预算、交付约定
├─ 01_SOURCE/         # 原始剧本、录音、实拍与不可替代源文件
├─ 02_REFERENCES/     # 角色、场景、风格、首尾帧参考
├─ 03_GENERATIONS/    # AI 输出，继续按 SCxx/SHxxx 分组
├─ 04_EDIT/           # 剪辑、合成、调色工程及代理文件说明
├─ 05_AUDIO/          # 对白、环境声、音效、音乐、混音
├─ 06_EXPORTS/        # 审核版、母版、平台版、无字版
├─ 07_DELIVERY/       # 只放本次正式交付包
└─ 99_ARCHIVE/        # 收集后的可恢复项目与清单
```

数字前缀只是为了稳定排序，不代表这是唯一结构。真正重要的是三条边界：

- 原始素材与派生素材分开；
- 工作导出与正式交付分开；
- 可重新生成的缓存与不可替代的源文件分开。

`03_GENERATIONS` 内再按镜头身份组织，而不是继续堆在日期文件夹里：

```text
03_GENERATIONS/SC03/SH014/
├─ INPUTS/            # 当次使用的参考素材快照
├─ CANDIDATES/        # 未筛选或待比较输出
├─ SELECTS/           # 进入剪辑的候选
└─ LOG/               # Prompt、参数、决定与淘汰原因
```

## 先“收集工程”，再把它叫作归档

剪辑工程通常保存的是素材引用，不是把所有视频都装进一个工程文件。因此项目在原电脑上能打开，不代表复制工程文件以后还能打开。

[Adobe 关于迁移 Premiere 项目的官方说明](https://helpx.adobe.com/uk/premiere/desktop/organize-media/create-projects/move-project-to-another-computer.html)建议使用 Project Manager 的 `Collect Files and Copy to New Location` 收集文件，并在迁移时保持文件结构；也可以选择统一转码，或排除未使用素材。[DaVinci Resolve 的官方编辑指南](https://documents.blackmagicdesign.com/UserManuals/DaVinci-Resolve-18-Editors-Guide.pdf)同样提供 Media Management 与项目归档工作流，可复制已用媒体、保留额外 handles，并重新链接到新位置。

这些功能可以帮助收集，但不能替你决定“什么值得长期保留”。个人 AI 视频项目至少保留：

1. 能重新打开的主工程或交换文件；
2. 最终采用的源素材和必要 handles；
3. 不可重建的参考图、录音、授权文件与 Prompt 快照；
4. 最终母版、字幕、音频分轨和封面；
5. 版本账、README 和交付清单；
6. 恢复项目所需的软件版本、字体、插件或替代方案说明。

> [!TIP]
> 不要在唯一工作盘上直接执行“排除未使用素材”后删除原件。先把收集结果放到新位置，重新打开、抽查时间线和音频，再决定旧素材的保留策略。

## 备份的重点不是“复制过”，而是“恢复过”

[Backblaze 对 3-2-1 原则的说明](https://www.backblaze.com/blog/the-3-2-1-backup-strategy/)是：保留三份数据，放在两个不同设备或介质上，其中一份异地。它也把 3-2-1 描述为现代数据保护的起点，而不是能覆盖所有风险的终点。

对个人创作者，一个可执行的起点可以是：

- 工作副本：当前剪辑盘；
- 本地副本：另一块独立硬盘或 NAS；
- 异地副本：云备份或不在同一地点的存储。

但“看到文件数量一样”仍不足以证明可恢复。归档完成以后至少做一次恢复抽查：

1. 把归档复制到一个新的路径；
2. 断开原始素材盘或临时改名，避免工程偷偷引用旧路径；
3. 打开工程并检查是否有离线素材；
4. 播放关键时间线、字幕、声音和合成段；
5. 从归档工程重新导出一个短片段；
6. 记录恢复日期、结果和未解决依赖。

如果文件很多，可以为交付包生成 SHA-256 校验清单。校验值不能证明内容“正确”，但能帮助确认传输前后的字节是否一致。

## 交付包只放“要交的”，不要复制整个工作现场

交付包应先服从双方约定。如果没有明确约定，可以用下面这张清单启动沟通，而不是自行假设对方需要所有工程文件。

| 目录 | 可能包含 | 交付前确认 |
| --- | --- | --- |
| `01_MASTERS` | 高质量母版、无字版、干净版 | 分辨率、帧率、编码、色彩、声道 |
| `02_PLATFORM` | 横版、竖版、短版、压缩版 | 平台规格和安全区 |
| `03_CAPTIONS` | SRT、双语字幕、烧录参考 | 时间码、断句、错字、帧率基准 |
| `04_AUDIO` | 混音、对白、音乐、音效分轨 | 采样率、峰值、声道、起始时间 |
| `05_PROJECT` | 收集后的工程或交换文件 | 软件版本、插件、字体、离线素材 |
| `06_RIGHTS` | 音乐、字体、图片和模型来源说明 | 授权范围、期限、待确认事项 |
| `07_MANIFEST` | README、文件清单、校验值 | 数量、大小、版本、联系人 |

README 不需要写成长文，但应该让第一次打开项目的人知道：

```text
项目：
本次交付版本：
交付日期：
主母版文件：
画面与声音规格：
字幕与字体说明：
工程软件与版本：
已知限制 / 待确认项：
文件清单与校验文件位置：
```

## 交付前做一次“陌生人测试”

把自己当成没有参与制作的接收方，按顺序检查：

### 1. 身份是否清楚

文件名能否看出项目、版本和用途？同名文件是否内容不同？主母版是否只有一个明确入口？

### 2. 规格是否匹配

不要只看扩展名。逐项核对分辨率、帧率、时长、编码、色彩、音频声道、字幕格式和平台比例。

### 3. 内容是否完整

检查首尾黑帧、字幕断句、拼写、口型、声音起止、音乐淡出、片尾信息和无字版差异。

### 4. 工程是否可恢复

从交付路径打开工程；不要让它继续引用桌面、下载目录或原始工作盘。

### 5. 来源是否能说明

对参考图、音乐、字体、实拍、合成素材和生成工具分别记录来源与已知授权范围。无法确认的项目直接标成“待确认”，不要用一句“AI 生成”替代来源记录。

> [!KEY POINT]
> 交付完成的标准不是“上传进度到了 100%”，而是接收方知道该打开什么、拿到了约定内容，并且关键文件经过规格、完整性和可恢复性检查。

## 把归档动作放进每天，而不是项目最后一天

最省力的归档不是收尾时做一次大扫除，而是在制作过程中维持几个固定动作：

- 新镜头建立时先分配 `SCxx_SHxxx`；
- 每次生成保存输入快照和批次编号；
- 每轮筛选记录采用与淘汰原因；
- 每天结束同步版本账并完成独立备份；
- 每个审核节点只发布一个明确 review 版本；
- 锁定画面后收集工程并执行恢复测试；
- 正式交付从干净目录重新组包，不从聊天记录里捞文件。

这样做不会让创作变得更“行政化”。恰恰相反，它把“这个文件到底是什么”的注意力成本拿走，让下一次修改能够从明确的镜头、版本和决定继续。
